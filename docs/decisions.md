# Journal des décisions

Ce journal accompagne la refonte hexagonale (mission : `REFACTO.md`, règles permanentes : `CLAUDE.md`). Il contient :

- une entrée datée pour chaque choix qui ne va pas de soi (une dépendance, une divergence voulue par rapport à l'existant, une règle déplacée, un cas non prévu par la mission) ;
- une entrée récapitulative par phase : ce qui a été fait, et ce qui a changé pour l'utilisateur (normalement rien).

Une règle autrefois portée par un commentaire du code y arrive quand elle ne peut devenir ni un test nommé, ni une fonction ou une constante nommée.

Format d'une entrée :

```
### AAAA-MM-JJ — Titre court
- Contexte : ce qui pose question, avec les faits.
- Décision : ce qui est retenu, et pourquoi.
- Conséquence : ce que cela change, ce qu'il faudra surveiller.
```

### 2026-10-15 — Code hérité compilé avec `noUncheckedIndexedAccess` sans changement de comportement
- Contexte : avec `noUncheckedIndexedAccess`, `tsc --noEmit` signalait 62 erreurs dans 10 fichiers de `src/` hors tests (`pipeline.ts` 26, `listings/normalize.ts` 12, `sources/email/parse.ts` 11, `sources/sites.ts` 4, `sources/http.ts` 2, `listings/brands.ts` 2, `demo.ts` 2, puis `server.ts`, `messages/templates.ts` et `api.ts` 1 chacun). Consigne : aucun `!`, aucun `as unknown as`, et un résultat identique pour chaque entrée.
- Décision : trois procédés, choisis au cas par cas pour que le diff reste le plus court possible.
  1. **Type seul**, sans effet sur le JS émis, quand l'invariant est local et visible :
     - `src/api.ts` (`GET /api/vehicles?status=ecartees`) : `counts` est typé `{ suivies: number; [kind: string]: number }` au lieu de `Record<string, number>`. `suivies` vaut 0 à l'initialisation, donc `counts.suivies++` reste valide.
     - `src/demo.ts` : `DEMO_LISTINGS` est typé `[RawListing, RawListing, ...RawListing[]]`. C'est un littéral de 10 annonces, utilisé seulement dans `demo.ts` ; `seedDemo` lit `[0]` et `[1]`.
     - `src/pipeline.ts` (`repair`) : `groups` est typé `Array<[(typeof keyed)[number], ...typeof keyed]>`. Un groupe naît toujours de `groups.push([k])` et ne fait ensuite que grandir, donc `x[0]` et `g[0]` (`first`) existent toujours.
  2. **Garde sur le résultat d'une regex** dont le groupe capturant est obligatoire. Si la regex correspond, `m[n]` est défini, donc `m[n] === undefined` équivaut à « pas de correspondance » :
     - `src/listings/brands.ts` (`detectBrand`) : `if (!m || m[1] === undefined) continue;`. Le groupe 1 `(^|[^\p{L}])` participe toujours ; il peut valoir `''`, ce qui est défini.
     - `src/sources/http.ts` (`robotsAllows`) : `if (!m || m[1] === undefined || m[2] === undefined) continue;`. Les groupes `([a-z-]+)` et `(.*)` sont obligatoires.
     - `src/sources/email/parse.ts` (`parseDepartment`) : `if (!m || m[1] === undefined) return undefined;`.
     - `src/sources/email/parse.ts` (`findBlock`) : `const last = idx[idx.length - 1]; if (last !== undefined)` remplace `if (idx.length)`. Le tableau `idx` est dense (`map` puis `filter`), donc l'équivalence est exacte.
     - `src/sources/email/parse.ts` (`pickTitle`) : `headingEl[0] ? … : ''` remplace `headingEl.length ? … : ''`. Après `.first()`, l'objet Cheerio contient 0 ou 1 élément, et un élément est un objet, donc vrai.
     - `src/pipeline.ts` (`repair`) : ajout de `if (!anchor) continue;`. Comme `if (!listings.length) continue;` précède, `keyed` (obtenu par `listings.map`) a au moins un élément, et cet élément est un objet.
     - `src/sources/email/parse.ts` (`parseHtml`) : `const ref = group[0]?.ref; if (!ref) continue;`. Chaque groupe de la `Map` naît avec une ancre (`g.push(a)` avant `groups.set`). Un `ListingRef` est un objet, donc vrai.
     - `src/sources/email/parse.ts` (`findBlock` et `commonAncestor`) : `const head = els[0]; if (!head) return [];` (même raison : un groupe n'est jamais vide). Ensuite, `head` est passé à `commonAncestor(head, els)` à la place de `els[0]`. C'est le même objet : `group[0].el` vu comme `AnyNode`.
  3. **`?? ''` sur un accès dont l'indice est garanti dans les bornes** (repli jamais emprunté) :
     - `src/listings/normalize.ts` : `m[1]` des regex `after`, `before`, `labelled` (`parsePrice`), `re` (`parseKm`) et de la regex « Ville (33) » (`parseLocation`), dont le groupe 1 est obligatoire ; `words[0]` et `words[words.length - 1]` (`trimConnectors`), derrière `words.length &&` ; `tokens[i]` et `tokens[j]` (`parseLocation`), bornes de boucle `0 ≤ j < tokens.length` ; `out[out.length - 1]` (`extractModel`), derrière `out.length &&`.
     - `src/sources/email/parse.ts` : `texts[…][0]` et `candidates[…][0]` (`pickTitle`), derrière `if (texts.length)` et `if (candidates.length)` ; `lines[j]` (`parseText`), avec `max(0, i-8) ≤ j ≤ i-1`.
     - `src/sources/sites.ts` : `m[1]` (`listingRef`), car tous les motifs de `SITES[].listing` ont un groupe 1 obligatoire et `own` vient toujours de `SITES` ; `split('.')[0]` (`prettyHost`), car `split` renvoie au moins un élément ; `meta[1]` (`resolveRedirect`), groupe obligatoire.
     - `src/server.ts` : `req.url.split('?')[0]`, pour la même raison que `prettyHost`.
     - `src/messages/templates.ts` (`pickVariant`) : `variants[h % variants.length]`, derrière `if (!variants.length) return ''`, avec `h ≥ 0` (`>>> 0`).
- Conséquence : `tsc --noEmit -p tsconfig.json` ne signale plus d'erreur, et chaque repli ajouté est inatteignable pour la raison indiquée. Une comparaison différentielle exécute l'ancien code (`git archive HEAD src`) et le nouveau sur le même corpus : toutes les fixtures d'emails et de pages, les 1 232 lignes de texte qui en sont extraites, les URL qu'elles contiennent et des cas limites (chaîne vide, `'.'`, `'www.'`, robots.txt vides ou mal formés, redirections simulées). Elle couvre `parsePrice`, `parseKm`, `parseYear`, `parseLocation`, `extractModel`, `extractVehicleInfo`, `detectBrand` (avec et sans marques personnalisées), `listingRef` (avec et sans site indice), `prettyHost`, `resolveRedirect`, `robotsAllows`, `listingsFromJsonLd`, `parseAlertEmail` (HTML et texte, 6 expéditeurs) et `pickVariant`, exceptions comparées par type : 17 066 comparaisons, 0 différence. `Pipeline.repair` a été comparé de la même façon avec une horloge figée (`seedDemo`, une annonce en double, puis des annonces rendues incompatibles pour provoquer 2 scissions) : base identique, identifiants et dates compris. La caractérisation de l'API (plus bas) passe aussi sur les sources de `HEAD`.

### 2026-10-15 — Test d'architecture : un moteur de règles pur, lu sur l'AST de `parseAst` (Vite)
- Contexte : la règle de dépendance et les interdits de `CLAUDE.md` (commentaires, `as`, état global) doivent bloquer dès la phase 1, sans faux positifs sur les URL et les regex, et sans dépendance de plus.
- Décision : `tests/architecture.test.ts` s'appuie sur un moteur de règles pur, rangé dans `tests/support/architecture/`, qui prend des fichiers en mémoire (`{ path, text }`) et rend des violations (`{ rule, path, line, message }`). Chaque message nomme le fichier, la ligne et l'import ou le texte fautif. L'AST vient de `parseAst` de `vite` (oxc via rolldown), avec `lang` choisi d'après l'extension (`ts`, `tsx`, `js`, `jsx`) et `sourceType: 'module'`. Le moteur parcourt l'AST de façon générique (gardes de type sur `unknown`), sans dépendre des types de `@oxc-project/types`, un paquet transitif. Un fichier que le parseur refuse produit une violation `syntax` : il n'est jamais ignoré en silence. Un fichier, un concept : `ast.ts`, `location.ts`, `target.ts`, `imports.ts`, `dependencies.ts`, `sharedTypes.ts`, `globalState.ts`, `purity.ts`, `comments.ts`, `assertions.ts`, `placement.ts`, `findViolations.ts`, `exceptions.ts`, `legacy.ts`, `biomeLegacyOverride.ts`, `violation.ts` et `sourceTree.ts`, seul à lire le disque (sources et `biome.json`). 78 tests : 74 sur des échantillons nommés d'après une situation réelle, 4 sur l'arborescence réelle (règles, exceptions périmées, exceptions injustifiées, override Biome).
- Conséquence : le test passe tant que `src/domain`, `src/application`, `src/infrastructure`, `src/shared` et `client/` n'existent pas, puisque le code hérité est couvert par les exceptions transitoires. Il devient contraignant dès qu'un fichier apparaît dans une couche. Les échantillons ont été vérifiés par mutation : neutraliser une détection (littéraux, `createHash`, zones, `import type`, `as unknown as`, `let`, `import()`, `export *`, entrées vides…) fait échouer au moins un test.

### 2026-10-15 — Détection des imports et résolution vers une couche
- Contexte : la règle de dépendance doit voir tous les chemins par lesquels un module en atteint un autre.
- Décision : un import, c'est `import … from` et `import type … from`, `export … from`, `export type … from` et `export * from`, `import('…')` dynamique, `import('…').Type` dans une position de type, et `import x = require('…')` (ou `import type x = require('…')`), forme TypeScript que `tsc` accepte avec les options du projet et qui contournait la règle avant la relecture. Un spécifieur relatif est résolu par rapport au dossier du fichier (`posix.normalize`), puis classé par préfixe, extension ignorée : `./x.js` vise bien `x.ts`. Un spécifieur nu est un module Node s'il commence par `node:` ou s'il est intégré à Node (`isBuiltin`), un paquet npm sinon. Un `import()` dont le chemin est calculé, ou un chemin absolu, est « non vérifiable » et refusé dans les couches régies. « Import type » s'entend au niveau de la déclaration (`import type { X }`, `export type { X } from`) : avec `verbatimModuleSyntax`, `import { type X }` laisse un import exécutable. La zone d'infrastructure est le premier dossier sous `src/infrastructure/` ; pour un fichier posé directement dans `src/infrastructure/`, c'est son nom sans extension.
- Conséquence : les règles appliquées sont les suivantes.
  - `domain` : seulement `src/domain/`, plus `import { createHash } from 'node:crypto'` en import statique dont tous les noms sont `createHash`.
  - `application` : seulement `src/application/` et `src/domain/`.
  - `infrastructure/<zone>` : `src/domain/`, `src/application/`, `src/shared/`, sa propre zone, les paquets npm et les modules Node. Le reste est refusé : une autre zone (même en `import type`, puisqu'un adaptateur ne connaît pas les autres), `main.ts`, `cli/` et le code hérité.
  - `shared` : seulement `import type` (ou `export type … from`) depuis `src/shared/`, et aucune déclaration exécutable ; sont permis les `type` et `interface`, exportés ou non, et `export type { … }`.
  - `client` : `client/`, `src/shared/` en `import type` seulement, et les paquets npm (`virtual:` compris). Les modules Node sont refusés, puisque c'est du code navigateur.
  - Seuls `src/main.ts` et `src/cli/` importent `src/infrastructure/` hors de l'infrastructure ; pour les couches régies, c'est déjà contenu dans leur liste blanche, donc cette règle ne vise en propre que le code hérité.
  - Aucune règle de dépendance pour les tests (`tests/**`, `*.test.*`, `*.spec.*`), `main.ts` et `cli/`. Les nouvelles couches ne peuvent pas importer le code hérité : l'ancien fichier ré-exporte le nouveau, jamais l'inverse. Si un fichier hérité doit ré-exporter un adaptateur (phase 3), il faudra lui accorder l'exception `compositionRoot` dans `legacy.ts` et le consigner ici.

## Tests migrés

Les 68 tests d'origine (7 fichiers, `npx vitest run --reporter=verbose src` : 68 réussis au commit `3f0e0c8`) migrent sous `tests/` selon la disposition de `PLAN.md`. Aucun ne disparaît.

Tous les noms d'origine sont en anglais, et `CLAUDE.md` exige un nom qui décrit la situation en français courant : chaque test reçoit donc un nouveau nom. La destination est relative à `tests/`.

La phase est celle où le test quitte `src/`. Phase 1 pour les tests dont le sujet entre dans le domaine. Phase 2 pour les tests d'application ainsi que pour les tests d'extraction et de lecture HTTP : ceux-ci sont rangés sous `tests/infrastructure/`, puis rebranchés sur leur adaptateur en phase 3. Ainsi, plus aucun test ne reste dans `src/` à la fin de la phase 2.
